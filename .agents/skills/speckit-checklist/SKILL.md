## 检查表目的："需求文字的单元测试"

**核心概念**：检查表是**需求写作的单元测试**，用于校验某个领域内需求的质量、清晰度和完整性。

**不是用于验证/测试实现**：

- 不是“验证按钮是否能正确点击”
- 不是“测试错误处理是否正常工作”
- 不是“确认 API 返回 200”
- 不是检查代码/实现是否匹配规格

**用于需求质量校验**：

- “是否为所有卡片类型定义了视觉层级要求？”（完整性）
- “是否用具体尺寸/位置量化了‘突出展示’？”（清晰度）
- “所有交互元素的 hover 状态要求是否一致？”（一致性）
- “是否定义了键盘导航的可访问性要求？”（覆盖率）
- “规格是否定义了 logo 图片加载失败时的行为？”（边界情况）

**类比**：如果规格是用自然语言写的代码，那么检查表就是它的单元测试套件。你测试的是需求是否写得好、是否完整、是否无歧义、是否已准备好实现，而不是实现本身是否可工作。

## 用户输入

```text
$ARGUMENTS
```

继续之前，你**必须**先考虑用户输入（如果输入不为空）。

## 输出语言要求

除非用户明确要求使用其他语言，否则本命令生成或更新的所有用户可见 Markdown 检查表内容都必须使用简体中文。保留代码标识符、文件路径、命令、占位符、检查项 ID（如 `CHK001`）、需求 ID（如 `FR-###`）、场景 ID（如 `US1`）以及其他机器可读 token 的原文。

## 执行前检查

**检查扩展 hook（检查表生成前）**：
- 检查项目根目录下是否存在 `.specify/extensions.yml`。
- 如果存在，读取它，并查找 `hooks.before_checklist` 下的条目。
- 如果 YAML 无法解析或内容无效，静默跳过 hook 检查并正常继续。
- 过滤掉 `enabled` 明确为 `false` 的 hook。没有 `enabled` 字段的 hook 默认视为启用。
- 对剩余 hook，**不要**尝试解释或求值 hook 的 `condition` 表达式：
  - 如果 hook 没有 `condition` 字段，或该字段为 null/空值，则视为可执行。
  - 如果 hook 定义了非空 `condition`，跳过该 hook，把条件求值留给 HookExecutor 实现处理。
- 从 hook 命令名构造 slash command 时，将点号 (`.`) 替换为连字符 (`-`)。例如：`speckit.git.commit` → `/speckit-git-commit`。
- 对每个可执行 hook，根据它的 `optional` 标记输出以下内容：
  - **可选 hook**（`optional: true`）：
    ```
    ## 扩展 Hook

    **可选前置 Hook**： {extension}
    命令： `/{command}`
    描述： {description}

    提示： {prompt}
    执行方式： `/{command}`
    ```
  - **强制 hook**（`optional: false`）：
    ```
    ## 扩展 Hook

    **自动前置 Hook**： {extension}
    正在执行： `/{command}`
    EXECUTE_COMMAND: {command}

    等待 hook 命令完成后，再继续执行步骤。
    ```
    输出上述区块后，你**必须**实际调用该 hook，并等待它完成后才能继续。调用方式应与你在当前 agent/session 中自行运行命令时一致（实际调用形式可能不同于上面展示的 `{command}` 字面 id，例如 skills 模式 agent 可能使用 `/skill:speckit-...` 或 `$speckit-...`）。只输出区块并不等于已经运行 hook。
- 如果没有注册 hook，或 `.specify/extensions.yml` 不存在，则静默跳过。

## 执行步骤

1. **设置**：从仓库根目录运行 `.specify/scripts/powershell/check-prerequisites.ps1 -Json`，并解析 JSON 中的 `FEATURE_DIR` 和 `AVAILABLE_DOCS` 列表。
   - 所有文件路径都必须是绝对路径。
   - 如果参数中包含单引号，例如 `"I'm Groot"`，使用转义语法：`'I'\''m Groot'`（如果可行，也可以使用双引号：`"I'm Groot"`）。

2. **如果存在**：加载 `.specify/memory/constitution.md`，获取项目原则和治理约束。

3. **澄清意图（动态）**：推导最多三个初始上下文澄清问题（不要使用预制问题目录）。这些问题必须：
   - 来自用户措辞 + 从 spec/plan/tasks 中提取的信号。
   - 只询问会实质改变检查表内容的信息。
   - 如果 `$ARGUMENTS` 中已经明确，则逐个跳过。
   - 优先精确，而不是追求宽泛覆盖。

   生成算法：
   1. 提取信号：功能领域关键词（例如 auth、latency、UX、API）、风险指示词（"critical"、"must"、"compliance"）、利益相关方线索（"QA"、"review"、"security team"）和明确交付物（"a11y"、"rollback"、"contracts"）。
   2. 将信号聚类为候选关注领域（最多 4 个），按相关性排序。
   3. 如果未明确，识别可能的受众与时机（author、reviewer、QA、release）。
   4. 检测缺失维度：范围宽度、深度/严格度、风险重点、排除边界、可衡量验收标准。
   5. 从这些原型中拟定问题：
      - 范围细化（例如“是否包含与 X 和 Y 的集成触点，还是仅限本地模块正确性？”）
      - 风险优先级（例如“这些潜在风险领域中，哪些应该设置强制门禁检查？”）
      - 深度校准（例如“这是轻量级提交前检查，还是正式发布门禁？”）
      - 受众框定（例如“这份检查表只供作者使用，还是也供同伴在 PR 评审中使用？”）
      - 边界排除（例如“本轮是否明确排除性能调优项？”）
      - 场景类别缺口（例如“未检测到恢复流程，回滚/部分失败路径是否在范围内？”）

   问题格式规则：
   - 如果提供选项，生成紧凑表格，列为：选项 | 候选项 | 为什么重要
   - 选项最多 A-E；如果自由文本答案更清晰，则省略表格。
   - 不要要求用户重复已经说过的内容。
   - 避免推测性类别（不要臆造）。不确定时，明确询问：“请确认 X 是否属于范围内。”

   无法交互时的默认值：
   - 深度：标准
   - 受众：如果与代码相关则为评审者（PR），否则为作者
   - 关注点：相关性最高的 2 个聚类

   输出问题（标记 Q1/Q2/Q3）。回答后，如果仍有 ≥2 个场景类别（替代流程 / 异常 / 恢复 / 非功能领域）不清晰，可以再问最多两个聚焦追问（Q4/Q5），每个追问附一行理由（例如“恢复路径风险未解决”）。总问题数不得超过五个。如果用户明确拒绝更多问题，跳过升级追问。

4. **理解用户请求**：组合 `$ARGUMENTS` 与澄清答案：
   - 推导检查表主题（例如 security、review、deploy、ux）。
   - 合并用户明确提到的必备项。
   - 将关注选择映射到类别骨架。
   - 从 spec/plan/tasks 推断缺失上下文（不要臆造）。

5. **加载功能上下文**：从 `FEATURE_DIR` 读取：
   - `spec.md`：功能需求和范围
   - `plan.md`（如果存在）：技术细节、依赖
   - `tasks.md`（如果存在）：实现任务

   **上下文加载策略**：
   - 只加载与当前关注领域相关的必要部分（避免整文件倾倒）。
   - 优先将长章节概括为简洁的场景/需求 bullet。
   - 使用渐进披露：只有发现缺口时再继续检索。
   - 如果源文档很大，生成中间摘要项，而不是嵌入原始文本。

6. **生成检查表**：创建“需求的单元测试”：
   - 如果 `FEATURE_DIR/checklists/` 不存在，则创建该目录。
   - 生成唯一检查表文件名：
     - 根据领域使用简短、描述性名称（例如 `ux.md`、`api.md`、`security.md`）。
     - 格式：`[domain].md`
   - 文件处理行为：
     - 如果文件不存在：创建新文件，条目从 CHK001 开始编号。
     - 如果文件已存在：向现有文件追加新条目，从最后一个 CHK ID 之后继续编号（例如最后一项是 CHK015，则新项从 CHK016 开始）。
   - 永远不要删除或替换现有检查表内容；始终保留并追加。

   **核心原则：测试需求，而不是测试实现**：
   每个检查表项都必须评估需求本身：
   - **完整性**：是否存在所有必要需求？
   - **清晰度**：需求是否无歧义且具体？
   - **一致性**：需求之间是否对齐？
   - **可衡量性**：需求是否能被客观验证？
   - **覆盖率**：是否覆盖所有场景/边界情况？

   **类别结构**：按需求质量维度分组：
   - **需求完整性**：是否记录了所有必要需求？
   - **需求清晰度**：需求是否具体且无歧义？
   - **需求一致性**：需求之间是否无冲突地对齐？
   - **验收标准质量**：成功标准是否可衡量？
   - **场景覆盖率**：是否覆盖所有流程/情况？
   - **边界情况覆盖率**：是否定义边界条件？
   - **非功能需求**：性能、安全、可访问性等是否已说明？
   - **依赖与假设**：依赖和假设是否已记录并验证？
   - **歧义与冲突**：哪些内容需要澄清？

   **如何编写检查表项："自然语言的单元测试"**：

   **错误**（测试实现）：
   - “验证落地页显示 3 张节目卡片”
   - “测试桌面端 hover 状态是否正常”
   - “确认点击 logo 会导航到首页”

   **正确**（测试需求质量）：
   - “精选节目的确切数量和布局是否已说明？[完整性]”
   - “‘突出展示’是否用具体尺寸/位置量化？[清晰度]”
   - “所有交互元素的 hover 状态要求是否一致？[一致性]”
   - “所有交互 UI 是否定义了键盘导航要求？[覆盖率]”
   - “logo 图片加载失败时的兜底行为是否已说明？[边界情况]”
   - “异步节目数据的加载状态是否已定义？[完整性]”
   - “规格是否定义了竞争 UI 元素之间的视觉层级？[清晰度]”

   **条目结构**：
   每个条目应遵循以下模式：
   - 使用问题格式询问需求质量。
   - 聚焦 spec/plan 中已经写明（或未写明）的内容。
   - 在方括号中包含质量维度 [完整性/清晰度/一致性/等]。
   - 检查既有需求时引用规格章节 `[Spec §X.Y]`。
   - 检查缺失需求时使用 `[缺口]` 标记。

   **按质量维度的示例**：

   完整性：
   - “是否为所有 API 失败模式定义了错误处理要求？[缺口]”
   - “是否为所有交互元素说明了可访问性要求？[完整性]”
   - “是否为响应式布局定义了移动端断点要求？[缺口]”

   清晰度：
   - “‘快速加载’是否用具体时间阈值量化？[清晰度, Spec §NFR-2]”
   - “‘相关节目’的选择标准是否明确定义？[清晰度, Spec §FR-5]”
   - “‘突出’是否用可衡量的视觉属性定义？[歧义, Spec §FR-4]”

   一致性：
   - “所有页面的导航要求是否一致？[一致性, Spec §FR-10]”
   - “落地页和详情页中的卡片组件要求是否一致？[一致性]”

   覆盖率：
   - “是否为零状态场景（无节目）定义了需求？[覆盖率, 边界情况]”
   - “是否覆盖并发用户交互场景？[覆盖率, 缺口]”
   - “是否为部分数据加载失败定义了需求？[覆盖率, 异常流程]”

   可衡量性：
   - “视觉层级要求是否可衡量/可测试？[验收标准, Spec §FR-1]”
   - “‘视觉权重平衡’是否可被客观验证？[可衡量性, Spec §FR-2]”

   **场景分类与覆盖**（聚焦需求质量）：
   - 检查是否存在这些场景的需求：主流程、替代流程、异常/错误、恢复、非功能。
   - 对每类场景询问：“[场景类型] 需求是否完整、清晰且一致？”
   - 如果缺少场景类别：“[场景类型] 需求是有意排除，还是遗漏？[缺口]”
   - 状态变更发生时包含韧性/回滚：“是否定义了迁移失败时的回滚要求？[缺口]”

   **可追踪性要求**：
   - 最低要求：≥80% 的条目必须包含至少一个可追踪引用。
   - 每个条目应引用：规格章节 `[Spec §X.Y]`，或使用标记 `[缺口]`、`[歧义]`、`[冲突]`、`[假设]`。
   - 如果没有 ID 系统：“是否建立了需求与验收标准 ID 方案？[可追踪性]”

   **暴露并解决问题**（需求质量问题）：
   围绕需求本身提问：
   - 歧义：“术语‘快速’是否用具体指标量化？[歧义, Spec §NFR-1]”
   - 冲突：“§FR-10 与 §FR-10a 的导航要求是否冲突？[冲突]”
   - 假设：“‘播客 API 始终可用’这一假设是否经过验证？[假设]”
   - 依赖：“外部播客 API 需求是否已记录？[依赖, 缺口]”
   - 缺失定义：“‘视觉层级’是否用可衡量标准定义？[缺口]”

   **内容整合**：
   - 软上限：如果原始候选条目 > 40，按风险/影响排序。
   - 合并检查同一需求方面的近似重复项。
   - 如果低影响边界情况 >5 个，创建一个合并条目：“需求是否覆盖边界情况 X、Y、Z？[覆盖率]”

   **绝对禁止**：这些会把检查表变成实现测试，而不是需求测试：
   - 任何以“验证”“测试”“确认”“检查” + 实现行为开头的条目。
   - 引用代码执行、用户动作、系统行为。
   - “正确显示”“正常工作”“符合预期运行”。
   - “点击”“导航”“渲染”“加载”“执行”。
   - 测试用例、测试计划、QA 流程。
   - 实现细节（框架、API、算法）。

   **必需模式**：这些是在测试需求质量：
   - “[场景] 是否已定义/说明/记录 [需求类型]？”
   - “[模糊术语] 是否用具体标准量化/澄清？”
   - “[章节 A] 与 [章节 B] 的需求是否一致？”
   - “[需求] 是否可被客观衡量/验证？”
   - “需求是否覆盖 [边界情况/场景]？”
   - “规格是否定义了 [缺失方面]？”

7. **结构参考**：生成检查表时遵循 `.specify/templates/checklist-template.md` 中的规范模板，包括标题、元信息区、类别标题和 ID 格式。如果模板不可用，使用：H1 标题、目的/创建时间元信息行、包含 `- [ ] CHK### <需求检查项>` 行的 `##` 类别章节，ID 从 CHK001 开始全局递增。

8. **报告**：输出检查表文件完整路径、条目数量，并总结本次是创建新文件还是追加到现有文件。总结：
   - 已选择的关注领域
   - 深度级别
   - 参与者/时机
   - 已纳入的用户明确必备项

**重要**：每次调用 `/speckit-checklist` 都使用简短、描述性的检查表文件名，并创建新文件或追加到现有文件。这样可以：

- 支持多种类型的检查表（例如 `ux.md`、`test.md`、`security.md`）
- 使用简单易记、能表达检查表目的的文件名
- 在 `checklists/` 文件夹中便于识别和导航

为避免混乱，使用描述性类型，并在完成后清理过时检查表。

## 检查表类型与示例条目

**UX 需求质量：** `ux.md`

示例条目（测试需求，而不是测试实现）：

- “视觉层级要求是否用可衡量标准定义？[清晰度, Spec §FR-1]”
- “UI 元素数量和位置是否已明确说明？[完整性, Spec §FR-1]”
- “交互状态要求（hover、focus、active）是否一致定义？[一致性]”
- “是否为所有交互元素说明了可访问性要求？[覆盖率, 缺口]”
- “图片加载失败时的兜底行为是否已定义？[边界情况, 缺口]”
- “‘突出展示’是否可被客观衡量？[可衡量性, Spec §FR-4]”

**API 需求质量：** `api.md`

示例条目：

- “是否为所有失败场景说明了错误响应格式？[完整性]”
- “限流要求是否用具体阈值量化？[清晰度]”
- “所有端点的认证要求是否一致？[一致性]”
- “是否为外部依赖定义了重试/超时要求？[覆盖率, 缺口]”
- “需求中是否记录了版本策略？[缺口]”

**性能需求质量：** `performance.md`

示例条目：

- “性能要求是否用具体指标量化？[清晰度]”
- “是否为所有关键用户旅程定义了性能目标？[覆盖率]”
- “是否说明了不同负载条件下的性能要求？[完整性]”
- “性能要求是否可被客观衡量？[可衡量性]”
- “是否定义了高负载场景下的降级要求？[边界情况, 缺口]”

**安全需求质量：** `security.md`

示例条目：

- “是否为所有受保护资源说明了认证要求？[覆盖率]”
- “是否为敏感信息定义了数据保护要求？[完整性]”
- “威胁模型是否已记录，且需求是否与其对齐？[可追踪性]”
- “安全要求是否与合规义务一致？[一致性]”
- “是否定义了安全失败/泄露响应要求？[缺口, 异常流程]”

## 反例：不要这样做

**错误：这些是在测试实现，不是在测试需求：**

```markdown
- [ ] CHK001 - 验证落地页显示 3 张节目卡片 [Spec §FR-001]
- [ ] CHK002 - 测试桌面端 hover 状态是否正常 [Spec §FR-003]
- [ ] CHK003 - 确认点击 logo 会导航到首页 [Spec §FR-010]
```

## 执行后检查

**检查扩展 hook（检查表生成后）**：
检查项目根目录下是否存在 `.specify/extensions.yml`。
- 如果存在，读取它，并查找 `hooks.after_checklist` 下的条目。
- 如果 YAML 无法解析或内容无效，静默跳过 hook 检查并正常继续。
- 过滤掉 `enabled` 明确为 `false` 的 hook。没有 `enabled` 字段的 hook 默认视为启用。
- 对剩余 hook，**不要**尝试解释或求值 hook 的 `condition` 表达式：
  - 如果 hook 没有 `condition` 字段，或该字段为 null/空值，则视为可执行。
  - 如果 hook 定义了非空 `condition`，跳过该 hook，把条件求值留给 HookExecutor 实现处理。
- 从 hook 命令名构造 slash command 时，将点号 (`.`) 替换为连字符 (`-`)。例如：`speckit.git.commit` → `/speckit-git-commit`。
- 对每个可执行 hook，根据它的 `optional` 标记输出以下内容：
  - **可选 hook**（`optional: true`）：
    ```
    ## 扩展 Hook

    **可选 Hook**： {extension}
    命令： `/{command}`
    描述： {description}

    提示： {prompt}
    执行方式： `/{command}`
    ```
  - **强制 hook**（`optional: false`）：
    ```
    ## 扩展 Hook

    **自动 Hook**： {extension}
    正在执行： `/{command}`
    EXECUTE_COMMAND: {command}
    ```
    输出上述区块后，你**必须**实际调用该 hook，并等待它完成后才能继续。调用方式应与你在当前 agent/session 中自行运行命令时一致（实际调用形式可能不同于上面展示的 `{command}` 字面 id，例如 skills 模式 agent 可能使用 `/skill:speckit-...` 或 `$speckit-...`）。只输出区块并不等于已经运行 hook。
- 如果没有注册 hook，或 `.specify/extensions.yml` 不存在，则静默跳过。
