## 用户输入

```text
$ARGUMENTS
```

继续之前，你**必须**先考虑用户输入（如果输入不为空）。

## 执行前检查

**检查扩展 hook（澄清前）**：
- 检查项目根目录下是否存在 `.specify/extensions.yml`。
- 如果存在，读取它，并查找 `hooks.before_clarify` 下的条目。
- 如果 YAML 无法解析或内容无效，静默跳过 hook 检查并正常继续。
- 过滤掉 `enabled` 明确为 `false` 的 hook。没有 `enabled` 字段的 hook 默认视为启用。
- 对剩余 hook，**不要**尝试解释或求值 hook 的 `condition` 表达式：
  - 如果 hook 没有 `condition` 字段，或该字段为 null/空值，则视为可执行。
  - 如果 hook 定义了非空 `condition`，跳过该 hook，把条件求值留给 HookExecutor 实现处理。
- 从 hook 命令名构造 slash command 时，将点号 (`.`) 替换为连字符 (`-`)。例如：`speckit.git.commit` → `/speckit-git-commit`。
- 对每个可执行 hook，根据它的 `optional` 标记输出以下内容：
  - **可选 hook**（`optional: true`）：
    ```
    ## 扩展 Hook

    **可选前置 Hook**： {extension}
    命令： `/{command}`
    描述： {description}

    提示： {prompt}
    执行方式： `/{command}`
    ```
  - **强制 hook**（`optional: false`）：
    ```
    ## 扩展 Hook

    **自动前置 Hook**： {extension}
    正在执行： `/{command}`
    EXECUTE_COMMAND: {command}

    等待 hook 命令完成后，再继续执行大纲。
    ```
    输出上述区块后，你**必须**实际调用该 hook，并等待它完成后才能继续。调用方式应与你在当前 agent/session 中自行运行命令时一致（实际调用形式可能不同于上面展示的 `{command}` 字面 id，例如 skills 模式 agent 可能使用 `/skill:speckit-...` 或 `$speckit-...`）。只输出区块并不等于已经运行 hook。
- 如果没有注册 hook，或 `.specify/extensions.yml` 不存在，则静默跳过。

## 执行大纲

目标：检测并减少当前功能规格中的歧义或缺失决策点，并将澄清结果直接记录到规格文件中。

说明：此澄清流程预期在调用 `/speckit-plan` 之前运行并完成。如果用户明确表示要跳过澄清（例如探索性 spike），可以继续，但必须提示后续返工风险会增加。

执行步骤：

1. 从仓库根目录**只运行一次** `.specify/scripts/powershell/check-prerequisites.ps1 -Json -PathsOnly`（组合 `--json --paths-only` 模式 / `-Json -PathsOnly`）。解析最小 JSON payload 字段：
   - `FEATURE_DIR`
   - `FEATURE_SPEC`
   - （可选）捕获 `IMPL_PLAN`、`TASKS`，供未来串联流程使用。
   - 如果 JSON 解析失败，中止并要求用户重新运行 `/speckit-specify`，或检查功能分支环境。
   - 如果参数中包含单引号，例如 `"I'm Groot"`，使用转义语法：`'I'\''m Groot'`（如果可行，也可以使用双引号：`"I'm Groot"`）。

2. **如果存在**：加载 `.specify/memory/constitution.md`，获取项目原则和治理约束。

3. 加载当前规格文件。使用以下分类法执行结构化歧义与覆盖扫描。对每个类别标记状态：清晰 / 部分清晰 / 缺失。生成用于优先级排序的内部覆盖图（除非不会提出任何问题，否则不要输出原始覆盖图）。

   功能范围与行为：
   - 核心用户目标和成功标准
   - 明确的非目标/范围外声明
   - 用户角色/persona 区分

   领域与数据模型：
   - 实体、属性、关系
   - 标识与唯一性规则
   - 生命周期/状态流转
   - 数据量/规模假设

   交互与 UX 流程：
   - 关键用户旅程/序列
   - 错误/空状态/加载状态
   - 可访问性或本地化说明

   非功能质量属性：
   - 性能（延迟、吞吐目标）
   - 可扩展性（水平/垂直扩展、限制）
   - 可靠性与可用性（uptime、恢复预期）
   - 可观测性（日志、指标、追踪信号）
   - 安全与隐私（authN/Z、数据保护、威胁假设）
   - 合规/监管约束（如有）

   集成与外部依赖：
   - 外部服务/API 及失败模式
   - 数据导入/导出格式
   - 协议/版本假设

   边界情况与失败处理：
   - 负向场景
   - 限流/节流
   - 冲突解决（例如并发编辑）

   约束与权衡：
   - 技术约束（语言、存储、托管）
   - 明确的权衡或被拒绝的替代方案

   术语与一致性：
   - 规范术语表
   - 避免使用的同义词/废弃术语

   完成信号：
   - 验收标准可测试性
   - 可衡量的 Definition of Done 风格指标

   其他 / 占位符：
   - TODO 标记/未解决决策
   - 缺少量化的模糊形容词（如 "robust"、"intuitive"）

   对每个状态为“部分清晰”或“缺失”的类别，加入一个候选问题机会，除非：
   - 澄清不会实质改变实现或验证策略。
   - 信息更适合延后到计划阶段（内部记录）。

4. 在内部生成按优先级排序的候选澄清问题队列（最多 5 个）。不要一次性输出全部问题。应用以下约束：
    - 整个会话最多 5 个问题。
    - 每个问题必须能用以下任一形式回答：
       - 简短多选（2-5 个互斥选项），或
       - 一个词/短语回答（明确限制：“不超过 5 个词”）。
    - 只包含会实质影响架构、数据建模、任务拆解、测试设计、UX 行为、运行就绪度或合规验证的问题。
    - 保持类别覆盖平衡：优先覆盖影响最高的未解决类别；当存在一个高影响区域（例如安全姿态）未解决时，不要用两个低影响问题取代它。
    - 排除已回答问题、琐碎风格偏好、计划层执行细节（除非阻塞正确性）。
    - 优先选择能降低后续返工风险或避免验收测试错位的澄清。
    - 如果超过 5 个类别仍未解决，按 (Impact * Uncertainty) 启发式选择前 5 个。

5. 顺序提问循环（交互式）：
    - 每次只提出**一个**问题。
    - 对多选问题：
       - **分析所有选项**，并根据以下因素确定**最适合的选项**：
          - 项目类型最佳实践
          - 类似实现中的常见模式
          - 风险降低（安全、性能、可维护性）
          - 与规格中可见的明确项目目标或约束对齐
       - 在顶部醒目展示你的**推荐选项**，并给出清晰理由（1-2 句解释为什么这是最佳选择）。
       - 格式：`**推荐：** 选项 [X] - <理由>`
       - 然后将所有选项渲染为 Markdown 表格：

       | 选项 | 描述 |
       |--------|-------------|
       | A | <选项 A 描述> |
       | B | <选项 B 描述> |
       | C | <选项 C 描述>（按需添加 D/E，最多 5 个） |
       | 简答 | 提供不同的简短答案（不超过 5 个词；仅在自由文本替代适用时包含） |

       - 表格后添加：`你可以回复选项字母（例如 “A”），也可以回复 “yes” 或 “recommended” 接受推荐，或提供你自己的简短答案。`
    - 对短答问题（没有有意义的离散选项）：
       - 基于最佳实践和上下文提供你的**建议答案**。
       - 格式：`**建议：** <你的建议答案> - <简要理由>`
       - 然后输出：`格式：简短回答（不超过 5 个词）。你可以回复 “yes” 或 “suggested” 接受建议，或提供你自己的答案。`
    - 用户回答后：
       - 如果用户回答 "yes"、"recommended"、"suggested"、“是”、“推荐”或“建议”，使用你之前给出的推荐/建议作为答案。
       - 否则，校验答案是否映射到某个选项，或符合 <=5 words 约束。
       - 如果含糊，要求快速澄清（仍算同一个问题；不要推进到下一个问题）。
       - 答案合格后，将其记录到工作记忆中（此时还不写盘），并进入队列中的下一个问题。
    - 满足以下条件时停止继续提问：
       - 所有关键歧义已提前解决（剩余队列项变得不必要），或
       - 用户表示完成（"done"、"good"、"no more"），或
       - 已提出 5 个问题。
    - 永远不要提前透露后续排队问题。
    - 如果一开始没有有效问题，立即报告没有关键歧义。

6. 每个被接受答案后的集成（增量更新方式）：
    - 维护规格的内存表示（启动时加载一次）以及原始文件内容。
    - 对本会话中第一个被集成的答案：
       - 确保存在 `## 澄清` 章节（如果缺失，根据规格模板放在最高层上下文/概览章节之后）。
       - 在其下创建（如不存在）今天的 `### 会话 YYYY-MM-DD` 子标题。
    - 接受答案后立即追加一条 bullet：`- 问：<question> -> 答：<final answer>`。
    - 然后立即将澄清应用到最合适的章节：
       - 功能歧义 -> 更新或添加“功能需求”中的 bullet。
       - 用户交互/参与者区分 -> 更新“用户故事”或“参与者”小节（如存在），加入澄清后的角色、约束或场景。
       - 数据形态/实体 -> 更新“数据模型”（添加字段、类型、关系），保留原有排序，并简洁记录新增约束。
       - 非功能约束 -> 在“成功标准 > 可衡量结果”中添加/修改可衡量标准（将模糊形容词转为指标或明确目标）。
       - 边界情况/负向流程 -> 在“边界情况 / 错误处理”下添加新 bullet（如果模板提供占位小节，可创建该小节）。
       - 术语冲突 -> 在整个规格中规范化术语；只有必要时保留原术语，并仅添加一次`（之前称为“X”）`。
    - 如果澄清使早前的模糊陈述失效，替换该陈述，不要重复；不要留下过时的矛盾文本。
    - 每次集成后都保存规格文件，以降低上下文丢失风险（原子覆盖）。
    - 保持格式：不要重排无关章节；保持标题层级不变。
    - 每条新增澄清都应最小化且可测试（避免叙事漂移）。

7. 校验（每次写入后执行，最终再执行一次）：
   - 澄清会话中每个已接受答案恰好对应一个 bullet（无重复）。
   - 已提问（已接受）问题总数 ≤ 5。
   - 更新后的章节中，不再残留本次答案本应解决的模糊占位。
   - 不存在矛盾的旧陈述（扫描并移除已失效替代选项）。
   - Markdown 结构有效；只允许新增标题：`## 澄清`、`### 会话 YYYY-MM-DD`。
   - 术语一致：所有更新章节使用同一规范术语。

8. 将更新后的规格写回 `FEATURE_SPEC`。

9. **重新校验规格质量检查表**（如果存在）：
   - 检查 `FEATURE_DIR/checklists/requirements.md` 是否存在。
   - 如果不存在，静默跳过本步骤。
   - 如果存在：
     1. 读取检查表文件。
     2. 识别所有 GitHub task-list checkbox 行：在代码围栏外匹配 `- [ ]`、`- [x]` 或 `- [X]` 的行（大小写不敏感，允许嵌套项前导空白）。忽略所有其他内容（标题、说明、非 checkbox bullet、元数据）。
     3. 对每个 checkbox 行，将当前 marker 状态（checked 或 unchecked）和条目文本记录到 before-snapshot 列表。
     4. 基于**更新后的**规格（步骤 7 刚保存的版本）重新评估每个 checkbox 条目。
     5. 对每个 checkbox 条目，仅当 checked/unchecked 状态确实变化时更新：
        - 如果条目现在通过且之前未勾选：将 `[ ]` 改为 `[x]`。
        - 如果条目现在失败且之前已勾选：将 `[x]`/`[X]` 改为 `[ ]`。
        - 如果状态未变：保持 marker 原样（保留现有大小写，避免无意义 diff）。
     6. 保存更新后的检查表文件。**只切换状态发生变化的 checkbox 行中的 `[ ]`/`[x]` marker 部分。** 所有其他文件内容（标题、元数据、备注、行顺序、空白）必须保持不变，以避免噪声 diff。
     7. 将 before-snapshot 与当前状态比较，计算完成报告所需的三个列表：
        - **新通过项**：从未勾选变为已勾选的条目。
        - **回退项**：从已勾选变为未勾选的条目。
        - **仍未勾选项**：仍未勾选的条目。
     8. 记录前后通过数，格式为 checked/total checkbox items（例如 "12/16 -> 15/16 items passing"）。

行为规则：

- 如果没有发现有意义的歧义（或所有潜在问题影响都很低），回复：“未发现值得正式澄清的关键歧义。”并建议继续。
- 如果规格文件缺失，要求用户先运行 `/speckit-specify`（不要在这里创建新规格）。
- 绝不超过 5 个总问题（同一问题的澄清重试不计为新问题）。
- 避免提出推测性技术栈问题，除非缺失信息阻塞功能清晰度。
- 尊重用户提前终止信号（"stop"、"done"、"proceed"）。
- 如果因覆盖充分而没有提问，输出紧凑覆盖摘要（所有类别“清晰”），然后建议进入下一步。
- 如果问题额度用尽但仍有高影响类别未解决，在“延后”下明确标出并说明理由。

优先级上下文：$ARGUMENTS

## 完成报告

在提问循环结束或提前终止后报告完成情况：
- 已提出并回答的问题数量。
- 更新后的规格路径。
- 触及的章节（列出名称）。
- 规格质量检查表状态（如果重新校验了 `FEATURE_DIR/checklists/requirements.md`）：展示前后通过数（例如“规格质量检查表：12/16 -> 15/16 项通过”），并列出所有状态变化项，包括新通过项（unchecked -> checked）和回退项（checked -> unchecked）。如果仍有未勾选项，将其列为需要关注的区域。
- 覆盖摘要表：列出每个分类类别及状态：已解决（原为“部分清晰/缺失”且已处理）、已延后（超过问题额度或更适合规划阶段）、清晰（已足够清晰）、未解决（仍为“部分清晰/缺失”但影响较低）。
- 如果存在“未解决”或“已延后”，建议是继续到 `/speckit-plan`，还是计划后再次运行 `/speckit-clarify`。
