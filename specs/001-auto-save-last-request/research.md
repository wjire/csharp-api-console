# 研究：自动保存最近一次请求记录

## 决策 1：复用现有请求历史存储

**决策**：继续使用 `RequestHistoryStore` 与 VS Code `workspaceState` 保存最近请求记录，在现有历史项上增加可选字段来保存 Headers、Body 模式和响应结果。

**理由**：项目已经有请求历史配置、TTL、数量限制、清空能力和敏感信息处理逻辑。复用该路径可以保持用户配置语义一致，并避免引入第二套状态存储导致历史来源不一致。

**已考虑的替代方案**：

- 新增独立 `lastRequest` 存储键：读取简单，但会和现有历史下拉、清空、TTL、敏感信息策略产生重复逻辑。
- 使用 WebView state 保存：只能覆盖当前 WebView 生命周期，无法满足关闭后重新打开仍恢复的需求。

## 决策 2：区分“可恢复输入”和“匹配上下文”

**决策**：保存并恢复的用户输入限定为 Auth、Headers、Query、Body；项目、Base URL、接口、HTTP 方法和路由模板用于构建历史匹配上下文，不作为用户输入覆盖当前面板结构。

**理由**：更新后的 FR-002 明确列出可复测请求输入为 Auth、Headers、Query、Body；FR-004 和假设仍要求同一项目、Base URL、接口维度恢复。将两者分开可以避免恢复历史时误改当前接口元信息。

**已考虑的替代方案**：

- 把方法、路由、Base URL 都当成可恢复输入：会超出更新后 FR-002 的用户输入范围，并可能覆盖当前面板初始化得到的接口上下文。
- 完全不记录 Base URL：改动少，但无法满足不同 Base URL 记录不串用。

## 决策 3：历史记录按 Base URL 隔离

**决策**：后续实现应把最近一次历史记录限定在项目、Base URL、HTTP 方法、路由模板等上下文内。WebView 在 Base URL 初始化或切换后请求对应范围的历史记录。

**理由**：规格要求不同 Base URL 的最近一次请求不能串用。当前历史键只按项目、方法和路由区分，无法区分同一接口在不同环境中的记录。

**已考虑的替代方案**：

- 继续沿用现有 endpoint key：改动少，但不满足不同 Base URL 隔离要求。
- 每个完整 URL 一条记录：隔离更细，但 Query 或路由占位符变化会导致同一接口的最近记录碎片化，不利于打开面板自动恢复。

## 决策 4：保存响应结果的可展示快照

**决策**：历史项保存响应展示所需的稳定快照，包括成功标记、状态码、响应头、响应体、耗时、错误信息和错误码。WebView 恢复时使用与请求完成相同的渲染路径展示该快照，但不触发重新发送。

**理由**：用户需要重新打开面板后直接看到上次响应结果。保存可展示快照能避免打开面板时依赖目标服务状态，也能明确这不是新的实时请求。

**已考虑的替代方案**：

- 只保存状态码：不足以满足“包括响应结果”。
- 打开面板时自动重新发送：可能造成误操作或写操作重复，不符合“不表示重新发送请求”的假设。

## 决策 5：按现有限制降级保存大内容

**决策**：请求 Body、FormData 文件内容、Binary 文件内容和响应体都应遵守大小限制；超限时保存空内容、摘要或元数据，并在恢复时保持可识别的降级展示。

**理由**：项目已提供 `requestHistoryMaxBodyKb` 来限制请求历史中的 Body 保存，继续沿用可控制 `workspaceState` 体积并保护性能。

**已考虑的替代方案**：

- 无限制保存完整请求和响应：恢复体验完整，但容易造成存储膨胀和 WebView 渲染性能问题。
- 完全不保存二进制和 FormData：实现简单，但会让 Body 模式恢复不一致。

## 决策 6：自动恢复只应用最新一条记录

**决策**：WebView 收到匹配历史列表后自动应用排序后的第一条历史记录，并将历史下拉选中该记录；用户之后手动修改输入不会覆盖历史，只有再次发送后才更新最新记录。

**理由**：`RequestHistoryStore.getHistory()` 已按时间倒序返回。自动应用第一条符合“最近一次”语义，也保留了下拉选择旧记录的现有能力。

**已考虑的替代方案**：

- 后端单独发送 `lastRequestLoaded`：语义清晰，但会和现有 `requestHistoryLoaded` 重复。
- 用户手动选择历史下拉：保留现状，但不能满足打开时自动恢复。
