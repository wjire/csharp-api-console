# 功能规格说明：自动保存最近一次请求记录

**功能分支**：`001-auto-save-last-request`

**创建日期**：2026-07-06

**状态**：草稿

**输入**：用户描述：`"测试面板打开时,所有的请求记录都是空的,需要用户填充,比如: Auth,Query,Body等,然后点击发送按钮,才会发起请求. 期望: 每次发送后,测试面板会自动保存最近一次请求的记录, 包括响应结果,下次打开测试面板时,可以直接看到上次发送的请求内容和响应结果,无需再次手动填充."`

## 用户场景与测试 *(必填)*

### 用户故事 1 - 重新打开测试面板自动恢复上次记录（优先级：P1）

作为 API 调试用户，我希望在重新打开同一个接口的测试面板时，自动看到最近一次发送过的请求内容和响应结果，这样我可以立即复查或重测，不需要重新填写 Auth、Query、Body 等内容。

**为什么是这个优先级**：这是本次需求的核心价值，直接减少重复输入并让用户可以延续上一次调试上下文。

**独立测试**：可以通过对某个接口填写请求信息并发送，关闭或重新打开该接口测试面板后验证请求内容和响应结果是否自动恢复，交付可直接复测的最小可用功能。

**验收场景**：

1. **给定** 用户在某个接口测试面板中填写 Auth、Query、Body 并成功发送请求，**当** 用户关闭后再次打开该接口测试面板，**则** 面板展示最近一次发送时的请求内容和响应结果。
2. **给定** 用户对同一接口连续发送多次请求，**当** 用户重新打开该接口测试面板，**则** 面板只恢复最后一次发送的请求内容和响应结果。
3. **给定** 用户重新打开测试面板后未做任何修改，**当** 用户点击发送，**则** 可以基于恢复出的请求内容再次发起同一次测试。

---

### 用户故事 2 - 新接口仍保持默认预填体验（优先级：P2）

作为 API 调试用户，我希望没有历史发送记录的接口仍然按当前默认规则打开，保留已有自动识别和预填能力，避免历史恢复行为影响首次测试。

**为什么是这个优先级**：该行为保护现有体验，避免新增功能让新接口或未测试接口出现错误数据。

**独立测试**：可以打开一个从未发送过请求的接口测试面板，确认面板没有错误恢复其他接口的请求或响应，同时仍展示当前系统已有的默认预填内容。

**验收场景**：

1. **给定** 某个接口从未发送过请求，**当** 用户打开该接口测试面板，**则** 面板不显示其他接口的请求记录或响应结果。
2. **给定** 某个接口没有最近一次请求记录但有当前系统可识别的默认参数，**当** 用户打开测试面板，**则** 默认参数仍按现有规则展示。

---

### 用户故事 3 - 不混淆不同调试上下文（优先级：P3）

作为 API 调试用户，我希望不同项目、Base URL 或接口的最近一次请求互不混淆，这样我不会因为恢复到错误上下文而误发请求。

**为什么是这个优先级**：该行为降低误操作风险，尤其是在多个项目或环境之间切换时。

**独立测试**：可以在不同项目、Base URL 或接口分别发送请求，再分别打开测试面板验证恢复内容只属于对应上下文。

**验收场景**：

1. **给定** 用户分别在两个不同接口发送过请求，**当** 用户打开其中任一接口测试面板，**则** 只恢复该接口最近一次请求和响应。
2. **给定** 用户在同一接口的不同 Base URL 下发送过请求，**当** 用户切换到其中一个 Base URL 并打开测试面板，**则** 只恢复该 Base URL 对应的最近一次请求和响应。

### 边界情况

- 最近一次请求没有响应或发送失败时，测试面板应恢复用户发送时的请求内容，并展示对应失败结果或错误信息。
- 最近一次请求存在超出系统保存限制的内容时，测试面板应清晰保留可恢复部分，并避免展示错误或过期内容。
- 历史记录损坏、缺失或无法读取时，测试面板应回退到没有历史记录的打开体验。
- 恢复的响应结果应明确对应最近一次已发送请求，避免用户误认为这是新发送的实时响应。
- 用户在面板中修改恢复出的内容后，只有再次发送才会更新最近一次请求记录。

## 需求 *(必填)*

### 功能需求

- **FR-001**：系统必须在用户每次发送测试请求后，保存该调试上下文下最近一次请求记录。
- **FR-002**：保存的最近一次请求记录必须包含用户发送时可见并可复测的请求输入，包括 Auth、Headers、Query、Body。
- **FR-003**：系统必须保存最近一次请求对应的响应结果，包括响应状态、响应头、响应内容、耗时或错误信息中当前面板可展示的内容。
- **FR-004**：用户打开同一项目、同一 Base URL、同一接口的测试面板时，系统必须自动恢复最近一次请求输入和响应结果。
- **FR-005**：当没有匹配的最近一次请求记录时，系统必须保持现有测试面板打开行为，不得恢复其他上下文的记录。
- **FR-006**：当用户对同一调试上下文发送新请求后，系统必须用新发送的请求和响应替换该上下文的最近一次记录。
- **FR-007**：系统必须在恢复记录时保留现有的敏感信息保护规则，不得引入超出当前产品策略的敏感数据暴露。
- **FR-008**：系统必须在最近一次响应不可完整恢复时提供一致的降级展示，用户仍能看到请求内容和可用的响应摘要或错误信息。
- **FR-009**：系统必须保证恢复出的请求输入可以被用户直接编辑，并且编辑本身不会覆盖已保存的最近一次记录。
- **FR-010**：系统必须避免不同项目、Base URL、接口或请求上下文之间的最近一次记录互相覆盖或串用。

### 关键实体 *(如果功能涉及数据则保留)*

- **测试请求记录**：代表用户最近一次发送测试请求时的输入状态，包括目标上下文、请求配置和可复测内容。
- **响应结果记录**：代表最近一次测试请求得到的结果，包括成功响应、错误响应或发送失败信息。
- **调试上下文**：用于区分记录归属的业务范围，至少包含项目、Base URL 和接口标识。

## 成功标准 *(必填)*

### 可衡量结果

- **SC-001**：用户在重新打开曾发送过请求的测试面板后，能在 3 秒内看到最近一次请求内容和响应结果。
- **SC-002**：在常规使用路径中，用户无需手动重新填写 Auth、Query、Body 即可完成同一接口的再次发送。
- **SC-003**：针对同一项目、Base URL 和接口，连续发送 5 次不同请求后，重新打开面板始终恢复第 5 次发送记录。
- **SC-004**：针对不同接口或不同 Base URL 的测试记录，恢复内容的串用率为 0。
- **SC-005**：当最近一次请求发送失败时，用户重新打开面板后仍能识别失败原因，并能基于原请求内容继续调整和重试。

## 假设

- “最近一次请求记录”按项目、Base URL 和接口维度保存，而不是全局只保存一条记录。
- 恢复范围覆盖当前测试面板已经支持展示和编辑的主要请求输入。
- 响应结果恢复用于复查上一次调试结果，不表示系统在打开面板时重新发送请求。
- 敏感信息保存遵循现有产品策略；本需求不扩大敏感信息保存范围。
- 对于超大请求体或响应体，沿用当前产品的大小限制和降级展示策略。
